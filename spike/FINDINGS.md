# M0 Findings — Trace-Format Spike

**Date:** 2026-09-04
**Verdict: GO.** All four core questions read YES for all three bindings. M1 proceeds
as designed; no spec rewrite is triggered.

This document is the formal answer PRD §11 requires before any code past this point
is kept. Every cell below cites the `AI/DECISION.md` entry that is its evidence — no
cell is asserted from memory or documentation; all six are backed by a real,
committed fixture trace, probed with `spike/probe.ts`.

## Verdict reasoning

**The first four rows are the core gate** (PRD §11: "does the trace carry the failed
action, its selector, the error class and a usable DOM snapshot"). All twelve cells
(4 questions × 3 bindings) read YES, each backed by a real trace generated by
running real Chromium against real fixture pages through each binding's actual test
runner — not inferred from documentation, which (per D-003) turned out to be
unreliable as a source during planning.

**Row 5 (title) is a bonus finding, not a gate condition**, but it closes what TRD §8
called an "open problem" and PRD §12 Q3 expected to remain open until M6. It closes
at M0 instead: the caller-set trace title is not just plausible (confirmed to exist
on the Java API during planning) but empirically confirmed to survive into the trace
file unmodified. TS and Python don't need this mechanism at all — their runners
auto-populate title for free (D-014, D-015), which is itself useful information: it
means `resolveIdentity()`'s title tier (TRD §8, D-008) works out of the box for two of
three bindings with zero user configuration.

**Row 6 (shadow DOM) is explicitly NOT a gate condition** — PRD §9 already defaults to
excluding shadow DOM from v1, and only asks M0 to check whether the exclusion can be
*lifted*. It cannot be lifted from this evidence alone (Python/Java untested), so the
default holds. This is a scope note for a future task, not a blocker: the TS finding
(shadow content is present, tagged, and structurally clean) means lifting the
exclusion later is plausible, not that it should happen now.

## What was different from the plan going in

Two things surfaced during M0 that the plan didn't anticipate, both resolved without
needing to stop and rewrite:

1. **The probe itself had a bug** (Task 7): first-seen sample-per-type selection
   under-detected `hasSelector` because the first `before` event in every trace is an
   empty test-hook call. Fixed by keeping the richest sample and scanning every event,
   not one sample, for the M0 checks (see D-014's write-up). This is exactly the kind
   of error D-003's "discover empirically, trust nothing from memory" policy exists to
   catch, and it caught it before a wrong finding reached this document.
2. **Python 3.12 needed installing** (Task 8) — the target machine only had 3.14.
   `py install 3.12` succeeded directly with no manual download; `pytest-playwright`
   installed cleanly with a prebuilt wheel. D-012's cautious fallback plan (generate
   the Python trace in CI instead) was not needed, but was correct to have had.

## Consequences for the rest of the plan

- **M1 (Tasks 12-20) proceeds exactly as planned.** `FailureRecord` (Task 12),
  failure-kind filtering (Task 13), and snapshot selection (Task 15) all have real
  evidence for their field assumptions now, not just the TRD's design.
- **Task 14's `resolveIdentity()`** should treat the trace-title tier as reliable for
  all three bindings (auto-populated for TS/Python, explicit for Java) rather than as
  a fallback-heavy path — the sidecar-JSON and filename-convention tiers exist for the
  case where a Java suite's tracing helper doesn't call `setTitle()`, not as the
  expected common path.
- **Shadow DOM stays excluded from v1** (no plan change). A natural point to revisit
  D-017 is candidate extraction (Task 16), which already has to decide how to walk
  every binding's snapshot tree — Python/Java shadow-DOM fixture traces could be
  generated there cheaply, superseding D-017 if they confirm parity.
- **No spec rewrite is triggered.** `mender-prd.md` and `mender-trd.md` stay at
  Draft v1.1 as written; this document supplements them with empirical grounding
  rather than replacing any of their content.
